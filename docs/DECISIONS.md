# Design decisions

A running record of why things are the way they are: what was chosen, why, and what the alternative was. Newest at the bottom.

| # | Date | Decision | Why | Alternative considered |
|---|---|---|---|---|
| 1 | 13 Oct 2026 | Cover EU, Spanish and UK data-protection and AI law, in English and Spanish, starting with Tier 1 documents | A corpus large enough to make retrieval choices matter; the EU/UK differences and changing law make it a harder problem than a single-law chatbot | A single-law assistant (the common case) |
| 2 | 13 Oct 2026 | Code under Apache-2.0; the texts keep their own licences (see `SOURCES.md`) | Patent grant, common in AI projects; keeps code and data licences clearly apart | MIT |
| 3 | 13 Oct 2026 | Chat model: Gemini 3.1 Flash-Lite, on a billing-enabled project for any public demo | Google's terms require paid services for apps available in the EEA, Switzerland and the UK; the model is cheap (about $0.0015 a question, estimated) | Open-weight models through a free host |
| 4 | 13 Oct 2026 | Deploy on Azure Container Apps with the image in GitHub Container Registry | Same free monthly grant as Cloud Run; Azure Container Registry has no free tier; adds a second cloud | Cloud Run (already known) |
| 5 | 13 Oct 2026 | An answer-model comparison is part of the plan (roadmap item 4.6) | Measure whether the default model is good enough instead of assuming | None: Flash-Lite only |
| 6 | 14 Oct 2026 | `src/` layout, one package (`law_assistant`), one test file per module, Python 3.12 in a `.venv` | Tests import the installed package, so they cannot pass by accident from the wrong folder; 3.12 is widely supported by AI libraries | Flat layout; Python 3.14 (newest, less library support) |
| 7 | 14 Oct 2026 | Test first for deterministic code; ruff for lint and format; CI runs lint, tests and a secret scan | Fetchers, parsers and chunkers have exact right answers, so tests can be written before the code | Tests after the code |
| 8 | 14 Oct 2026 | The HTTP client is the standard library behind a small `Client` interface; time and HTTP are passed in | No runtime dependency yet; tests use a fake client and a fake clock, so they never touch the network or sleep | `requests` or `httpx` |
| 9 | 14 Oct 2026 | Fetched documents go to `data/raw/` (git-ignored) with a `.meta.json` record: URL, retrieval time, hash, size, licence, credit, User-Agent | The sources have different licences and some must not be redistributed; the record is the "retrieval date" that `SOURCES.md` promises | Committing the raw files |
| 10 | 14 Oct 2026 | A document is fetched once and never again unless forced; writes are atomic (temporary file, then rename) | Fewer requests to public services; a failed or interrupted download can never leave a half-written file that looks valid | Always re-fetch |
| 11 | 14 Oct 2026 | Politeness rules in code: identifying User-Agent (a missing contact is an error), robots.txt honoured, at least 5 seconds between requests or the site's crawl delay if slower, http(s) URLs only | legislation.gov.uk requires an identifying agent and sets a 5-second crawl delay; the rules are also enforced by tests | Hand-written discipline |
| 12 | 14 Oct 2026 | robots.txt: a 4xx answer means no restrictions, any other failure stops the fetch | That is what RFC 9309 specifies; failing closed on server errors avoids ignoring rules we could not read | Treat every failure as "allowed" |
| 13 | 14 Oct 2026 | A small hand-written `.env` reader instead of a library | Four lines of behaviour, tested; avoids a dependency | `python-dotenv` |
| 14 | 14 Oct 2026 | EU acts are fetched from the Cellar API as XHTML, by CELEX number, with the language chosen by header | EUR-Lex's web pages answer scripts with a bot challenge, which we do not bypass; XHTML keeps stable ids for articles and recitals that the parser can use | Formex XML or PDF (harder to parse); scraping the website |
| 15 | 14 Oct 2026 | Keep both the Official Journal text and the consolidated text of each EU act | Recitals exist only in the Official Journal text; the consolidated text shows the law as currently amended and gives the as-of versions (AI Act: original 2024, consolidated 27 July 2026) | Consolidated only (loses the recitals) |
| 16 | 14 Oct 2026 | Every parser outputs one common record, `Provision` (id, instrument, jurisdiction, language, version, unit, kind, path, text, heading, chapter, order), saved as JSON Lines in `data/parsed/` | Chunking, retrieval and citations then work on one shape whatever the source markup; the path gives exact citations such as Article 6(1)(f) | One format per source |
| 17 | 14 Oct 2026 | The EU parser reads the XHTML with the standard-library XML parser and keeps structure from the markup's own ids (`art_6`, `rct_47`, `anx_III`) | The files are well-formed XML and the ids are stable; no HTML-parsing dependency needed | BeautifulSoup or lxml |
| 18 | 14 Oct 2026 | A parse is trusted only after structural checks: unique ids, no empty leaves, numbering without gaps, known totals (GDPR 99 articles and 173 recitals, AI Act 113 and 180 and 13 annexes, Omnibus 4 and 47), clean text, identical English and Spanish skeletons, and coverage of the source text | A parser fails quietly; these checks found six real markup differences before any text was used (see `docs/PARSING.md`) | Manual spot-checks only |
| 19 | 14 Oct 2026 | Tests on the real downloaded files are skipped when the files are absent (CI); small fixtures taken from the real markup carry the logic tests | CI never needs the raw data, which is git-ignored, and the real-file tests still run on any machine that has fetched it | Committing the raw files; mocking everything |
| 20 | 14 Oct 2026 | The Digital Omnibus (an amending act) is parsed with the same code: quoted blocks are read as text of their amendment point, data tables are kept row by row, and language-specific labels such as "14a" and "14 bis" are not compared between languages | The Omnibus matters for its dates and changes, not for a perfect article skeleton; nothing in it is lost (coverage 100.0%) | A separate parser for amending acts |
| 21 | 14 Oct 2026 | The line-length lint rule is relaxed for tests only | Long expected strings in tests are clearer unwrapped | Wrapping them |
| 22 | 14 Oct 2026 | The consolidated EU texts get their own parser, sharing only the id builder and the checks with the Official Journal parser | The two markups share nothing but the article ids (different class names, two-column grids instead of tables, amendment marks inside the text) | One parser with two modes |
| 23 | 14 Oct 2026 | Both versions of each EU text are kept side by side, labelled in the `version` field (`oj`, `consolidated-20160504`, `consolidated-20260727`), not merged | Recitals exist only in the Official Journal text; the consolidated text is the law as amended; the as-of logic needs both | Keep only the consolidated text |
| 24 | 14 Oct 2026 | A consolidated text is cross-checked against the Official Journal text id by id, ignoring spacing: every difference must be an amendment or a corrigendum. For the AI Act, every changed article must be one the Omnibus mentions | An independent check that the consolidated parse is right: the GDPR matches exactly apart from the 2018 corrigendum (16 wording changes in English, 38 in Spanish) | Spot-checking |
| 25 | 14 Oct 2026 | Language-dependent labels for inserted provisions (English 14a, Spanish "14 bis") are stored as written and normalised only when comparing the two languages | The stored ids stay faithful to each language's official numbering; the comparison still works | Normalising in the stored ids |
| 26 | 15 Oct 2026 | The UK parser takes each provision's place from the XML's own citation ids (`article-6-1-a`, `section-6A-2`, `schedule-1-paragraph-3-2-a`) | The ids are the official citations, so no numbering logic of ours can disagree with them | Counting and labelling levels ourselves |
| 27 | 15 Oct 2026 | Repealed and not-yet-in-force provisions are left out of the current text and counted; the only article or section numbers allowed to be missing are exactly those | The assistant must not quote law that is not in force; the check proves nothing else was dropped (UK GDPR Articles 60 to 76, 92 and 93; ten sections of the new Act not yet in force) | Including them with a flag |
| 28 | 15 Oct 2026 | `in_force_from` is the date from which the current version of the element, or of the text around it, applies (`RestrictStartDate`), not the date its own wording changed | It is what the source states; it agrees with the government's commencement table (Article 17(1)(g) 31 March 2026, section 103 19 June 2026); the later as-of logic can refine it | Leaving it empty |
| 29 | 15 Oct 2026 | The Provision model gains the units `section` and `schedule`, for the UK's sections and schedules | UK citations are "section 6" and "Schedule 1 paragraph 3", not articles and annexes; the UK GDPR keeps `article` and `annex` as in its text | Mapping sections to articles |
| 30 | 15 Oct 2026 | The BOE parser takes each provision's place from the block `titulo` ("Artículo 7"), not from the block id | The BOE ids (`a7`, `da-2`) are internal, not citations | Decoding the ids |
| 31 | 15 Oct 2026 | The BOE file holds every dated version of each block; the parser keeps the latest version whose date is not after `as_of`, and stores that date as `in_force_from` | This is how Spanish law is consolidated; it makes the as-of answers possible (nothing on 6 Dec 2018, 758 provisions on 7 Dec 2018, 763 today) | Parsing only the newest text |
| 32 | 15 Oct 2026 | In the BOE text, numbering markers are recognised by their text ("1.", "Uno.", "a)", "1.º", "–"), not by the paragraph class | The classes are used inconsistently within one article | Trusting the classes |
| 33 | 15 Oct 2026 | The BOE preamble becomes recitals (path: Roman section and paragraph number); editorial notes are not law text and are skipped | The preamble plays the role of recitals in retrieval; the notes are the BOE's commentary, though they are the proof of which blocks changed | Dropping the preamble; keeping the notes |
| 34 | 15 Oct 2026 | The Provision model gains the unit `disposition` (additional, transitional, repealing, final) | Spanish citations are "disposición final tercera", which is neither an article nor a schedule | Treating them as articles |
| 35 | 15 Oct 2026 | The chunk is the article, section, annex, schedule, disposition or recital; a longer unit splits at paragraphs, then points, then sentences, then words | Lawyers cite by these units; the profile showed three quarters of units fit as they are and 22% do not | Fixed-size windows over the text |
| 36 | 15 Oct 2026 | Starting cap of 400 words per chunk, a firm ceiling and a setting | From the length distribution (median 189, 90th percentile 653); it is a starting point to be tested in Phase 3, not a result | A guess without the profile |
| 37 | 15 Oct 2026 | Each chunk carries a context line (law, chapter, citation, heading) stored apart from its text and embedded with it | Short provisions are meaningless alone; keeping it separate lets Phase 3 measure its effect | Embedding the bare text |
| 38 | 15 Oct 2026 | A chunk stores the ids of its provisions; pinpoint citations (Article 6(1)(f)) are built from them later | Chunks stay readable text while exact citations remain recoverable | Storing a citation string per chunk |
| 39 | 15 Oct 2026 | Chunk ids are `<version>:<language>:<first provision id>` with `#n` for repeats; the build is deterministic and fails on any check problem | Experiments need the same chunks every time; ids survive a rebuild | Random or sequential ids |
| 40 | 15 Oct 2026 | A coverage figure below 100% is explained item by item before it is accepted | The 99.87% on the AI Act had been read as rounding; it was a whole annex missing, found only because the chunker refused an empty chunk | A fixed tolerance such as 99.5% |
| 41 | 15 Oct 2026 | The gold set is 80 questions: lookup 16, definition 8, cross-reference 10, EU-UK 10, Spanish law 8, as-of 10, numeric 8, refuse 10; 40 English and 40 Spanish; 40 development and 40 test, stratified | The mix covers the roadmap's types; with 40 test questions an 80% hit rate has an interval of about 12 points, and 100 questions would only narrow it to about 11, so size is not the lever (paired comparison is) | 100 questions |
| 42 | 15 Oct 2026 | Gold labels name the instrument and unit (with optional pinpoint ids, quotes, version and language), never a chunk | The chunking is an experiment variable (R3); labels must survive it | Chunk-level labels |
| 43 | 15 Oct 2026 | The gold is tied to the corpus snapshot of 14 Oct 2026, every question records its `as_of`, and any change after freezing is a new version with a new hash | The law changes; results from different versions of the scoreboard are not comparable | Editing the set in place |
| 44 | 15 Oct 2026 | Every gold fact is checked by script against the parsed text (unit, pinpoint ids, quotes); no lawyer has reviewed the set and the write-up will say so | The checks can prove the gold matches our texts, not that an interpretation is right | Unchecked gold |
| 45 | 15 Oct 2026 | A leakage warning compares each question with its gold text by word overlap weighted by word rarity across the corpus (advisory, 60%) | A question that copies its answer's wording rewards keyword search; the plain count flagged ordinary topic vocabulary, the weighted one did not hide that the plan's own example question was lexically close to Article 7 | Plain word counts |
| 46 | 15 Oct 2026 | About 15 gold questions are written by the person using the tool, as the realistic user, after seeing a topic map of the drafted ones; the test split is committed with a dated hash; the metrics module is step 2.4 | Reduces author bias; a public repo cannot hide the test set, so the discipline is procedural and logged | One author writes all; keep the test answers out of the repo |
| 47 | 15 Oct 2026 | Omitted provisions (a line of dots in the UK XML) are left out and counted like repealed ones, their article numbers are known gaps, and the coverage yardstick skips them | They carry no law text and the dots were being chunked, embedded and retrievable (181 provisions, 36 empty chunks); found by reviewing the gold set | Keeping them with an "omitted" flag |
| 48 | 15 Oct 2026 | Each gold answer is reviewed as a lawyer would: against the whole provision and its neighbours, not an extract, noting omissions, jurisdiction traps, version differences and application dates in the question's `notes` | The first batch had real errors (the data protection officer answer ignored Article 37(4), the high-risk AI duties ignored the postponed dates) | Fact-checking only the quotes |
| 49 | 15 Oct 2026 | A question about law that exists in parallel in the EU and the UK, or that Member States can vary, states its jurisdiction in the wording | Otherwise a correct UK or national chunk would count as a miss, or a user question would have no right answer | Accepting counterparts from every jurisdiction as relevant |
| 50 | 15 Oct 2026 | A gold provision whose wording differs between the original and consolidated text is pinned to one version; the original (OJ) text is gold only for as-of questions about it | A chunk of the superseded wording would give a wrong answer for today's law (AI Act Articles 4, 5, 6, 113 and the new Articles 4a and 75a to 75d) | Version-free labels |
| 51 | 15 Oct 2026 | When a gold provision lists pinpoint ids, a retrieved chunk is a hit only if it contains one of them; otherwise any chunk of the unit counts (to be implemented in step 2.4) | Definitions sit in one long article; a chunk with a different definition must not count as a hit | Unit-level hits |
| 52 | 15 Oct 2026 | `in_force_from` of a BOE provision is the date of its block's latest version, so it is not used paragraph by paragraph: the BOE as-of question is built on an article that was added later in a single version (53 bis) | Article 2(1) of the LOPDGDD reads the same in 2018 and today although its block is dated 2021 | Trusting the date for every paragraph |
| 53 | 15 Oct 2026 | The last 15 gold questions were drafted to fill the ways of asking that the first 65 did not cover (the `author` field of each question records who wrote it); all 80 are reviewed and any may be rewritten | The plan's aim of reducing author bias by having a person write 15 is not met, so the review has to carry it | A person writes 15 |
| 54 | 15 Oct 2026 | A third phrasing style, `terse` (keywords as typed into a search box), joins `lay` and `lawyer` | Real queries are often short and unpunctuated; retrieval behaves differently on them | Only full sentences |
| 55 | 15 Oct 2026 | Exact figures (fine ceilings, deadlines, ages, application dates) live in a committed JSON Lines table of typed facts, each with a one-line answer in English and Spanish, caveats and sources with quotes | Models misread numbers; a table returns the same verified value every time, and the roadmap's routing test (4.5) needs a table to route to | Reading figures out of retrieved prose |
| 56 | 15 Oct 2026 | Every number and date in a fact must be found in the provisions it cites (digits with grouped thousands, number words only where they count a period or an age, dates in both languages); the table is not written otherwise, and a negative control proves the check catches a corrupted figure | A check that has never failed proves nothing; "one of the following" must not count as the number one | Quote checks only |
| 57 | 15 Oct 2026 | Derived dates and ambiguous wordings are not stored as figures: they go in a caveat (the date for Article 101 fines, "mayor de catorce años") | The table must state only what a provision states | Storing the derived date as a fact |
| 58 | 15 Oct 2026 | Each numeric gold question's expected answer must state the figures of the fact it names | Two artefacts written separately that must agree catch errors in either | Trusting each alone |
| 59 | 15 Oct 2026 | hit@k, recall@k and MRR use primary gold provisions only; nDCG is graded (primary gain 3, acceptable gain 1); each gold provision is credited once, at the first chunk that satisfies it, and at most one per chunk | The index holds several copies of each text, so counting every copy would reward duplicates; one credit per target keeps the ideal ranking at 1 | Counting every matching chunk |
| 60 | 15 Oct 2026 | Only questions routed to retrieval are scored by these metrics (62 of 80); numeric and refusal questions are judged by the router | The table and the refusals are not retrieval problems | Scoring all 80 |
| 61 | 15 Oct 2026 | Intervals come from a seeded bootstrap over questions, and variants are compared with a paired bootstrap on the same questions; no numerical library is added | Small sets are noisy; pairing removes question-to-question noise; reproducibility needs a seed | Single scores without intervals; adding numpy |
| 62 | 15 Oct 2026 | Every gold provision must be satisfiable by at least one real chunk (checked by `unreachable_targets`), and an oracle ranking must score 1 and an empty one 0 | Otherwise a mistake in the gold would look like a retrieval failure | Trusting the gold |
| 63 | 15 Oct 2026 | The gold set was independently reviewed by five separate AI reviewer passes that saw only the question, the expected answer and the cited provision text; every finding was verified against the corpus before it was adopted | The author of a test is the worst reviewer of it; the first draft had 12 major findings (a false premise in an as-of question, a wrongly narrowed legal term, a wrong article) that scripts could not catch | Reviewing only by the author; asking a person to check the law |
| 64 | 15 Oct 2026 | The gold set is frozen with a manifest (SHA-256 fingerprint, date, seed, counts, review statement) and a CI test fails on any edit; a change makes a new version and results across versions are not comparable | Comparable experiments need a scoreboard that cannot drift | Editing in place |
| 65 | 15 Oct 2026 | The split is 40 development and 40 test, stratified by type and language, with seed 20261015 fixed before any result was seen and never re-drawn; each half has 31 retrieval questions | Re-drawing until the halves look right would be tuning on the test set | A free choice of seed |
| 66 | 15 Oct 2026 | The set carries an honest label: drafted by an AI assistant, checked by scripts, reviewed by five AI passes, not reviewed by a qualified lawyer or by a person for its legal content; expected answers are key-point references, not exhaustive treatments | A claim of review that did not happen would be worse than the gap; the write-up has to survive the question "who checked the law?" | Presenting it as reviewed |
| 67 | 15 Oct 2026 | The frozen gold set is approved for use in Phase 3, and a further round of independent review is planned near the end, before the final write-up; any change from it makes a new version | The first review caught 12 major problems; a later look with fresh eyes and the experiments' results in hand may catch more, and the freeze rule keeps the comparison honest | Treating the first review as final |
| 68 | 15 Oct 2026 | Phase 3 is pre-registered in docs/PHASE3_PLAN.md: primary metric recall@5, a variant is adopted only if the lower end of its paired 95 % interval of improvement is above 0, tuning on the development half only, the test half once per decision for the final pipeline against the R1 baseline, every variant counted and logged | Fixing the metric and the rule before any result stops the flattering choice being made afterwards; with 31 questions the bar is not lowered to compensate | Choosing the metric after seeing results |
| 69 | 15 Oct 2026 | BM25 is implemented in plain Python (no dependency), with the formula checked against a hand-computed example, ties broken by chunk id, and k1 = 1.2, b = 0.75 not tuned in R1 | No download or install is needed for the first real numbers, and the code is small enough to read and test | A search library |
| 70 | 15 Oct 2026 | R1.1 (BM25 plain, recall@5 0.24 on the development questions) is the baseline for later comparisons; accent folding (R1.2) is not better | The paired interval for R1.2 against R1.1 ends at 0.000 and R1.2 is not better in any resample | Keeping R1.2 |
| 71 | 15 Oct 2026 | The experiments run with BM25 while embeddings are unavailable (R3 chunk size, R8 version policy, R10 duplicate collapsing) are recorded as provisional and repeated with embeddings | A retriever that finds the right article for only about 30 % of required provisions cannot show the effect of tidying slots, versions or chunk sizes | Treating the BM25 results as final |
| 72 | 15 Oct 2026 | R2 uses reciprocal rank fusion with k = 60 and equal weights; a 2 to 1 weighting is tried only if the equal-weight version improves on the better single retriever in point estimate, and is compared with the better single retriever, not the weaker one | One constant and one conditional variant keep the number of comparisons small and the comparison hard | Tuning the constant and weights freely |
| 73 | 15 Oct 2026 | The embedding cache is keyed by model and prompt text, so identical chunks (3,831 chunks, 3,304 distinct prompts) are embedded once | 527 chunks are exact repeats (for example GDPR articles unchanged between the original and consolidated texts); paying twice would be waste | One vector per chunk id |
| 74 | 15 Oct 2026 | The open embedding model BGE-M3 (BAAI, MIT) is run locally on the graphics card: PyTorch 2.7.1 for CUDA 12.6 (a 2.7 GB package, chosen because that version still supports the card's architecture, checked after installing), transformers and numpy as the optional extra `open-embeddings`, and the model files (2.27 GB weights) in the git-ignored data/models | No key, no rate limit, no cost, repeatable; the core install, the tests and CI do not need any of it | Waiting for the hosted model's free tier |
| 75 | 15 Oct 2026 | The hosted embedding run (gemini-embedding-2, free tier) was stopped after it made no progress for 30 minutes at 640 of 3,304 vectors; the vectors are kept and it can resume | Google's free tier throttled sustained use beyond what the retry logic could wait out; it stays a candidate for R4 but no longer blocks Phase 3 | Letting it run |
| 76 | 15 Oct 2026 | BGE-M3 is the retriever that later experiments are measured against (recall@5 0.53 against BM25 0.24, paired interval +0.086 to +0.484); the embedding model itself is chosen when all R4 candidates have run | The pre-registered rule is met against the keyword baseline; one model does not make a comparison of models | Declaring the model chosen |
| 77 | 15 Oct 2026 | Reciprocal rank fusion of BM25 with BGE-M3 is not adopted (recall@5 0.43 against 0.53 for BGE-M3 alone) and the weighted variant is not run | Equal-weight fusion lets a much weaker list drag down a stronger one; the rule says weights are tried only if equal weights improve in point estimate | Tuning weights anyway |
| 78 | 15 Oct 2026 | R8 and R10 repeated with BGE-M3: nothing is adopted; the index keeps every version and results are not collapsed | Version policy and duplicate collapsing change recall@5 by -0.008 to -0.024 with every interval including 0; the losses are about ranking, not about crowding or superseded copies | Current-text-only or collapsed results |
| 79 | 15 Oct 2026 | Before choosing a reranker its ceiling is measured: only 65 % of required provisions are within BGE-M3's top 30 (44 % within the top 5, 89 % within the top 100), so a reranker over the top 30 can add about 21 points at most and a better first-stage search is pursued in parallel | A second-stage model cannot lift what the first stage never retrieved | Downloading a reranker first |
| 80 | 15 Oct 2026 | Cross-language retrieval is described, not tested, until more cross-language questions exist: three development questions, keyword 0 of 3 and BGE-M3 2 of 3 | Too few questions for a claim; it is recorded as a description | Claiming a cross-language result |
| 81 | 15 Oct 2026 | The context line stays in the embedded text of every chunk, and the 400-word cap stays | Removing the context line lowers BGE-M3's recall@5 from 0.53 to 0.37 (paired interval -0.315 to -0.016); no other cap beats 400 detectably (cap 200 +0.040, interval -0.089 to +0.177) | Embedding the law text alone; a smaller cap |
| 82 | 15 Oct 2026 | The reranker (bge-reranker-v2-m3) is not adopted; the download and the wrapper stay in the repository as an optional experiment | Reranking the top 30 gives recall@5 0.52 against 0.53 (paired -0.011, interval -0.151 to +0.129) and the top 50 0.53 (-0.003); it is 32 to 49 times slower (3.83 s and 5.91 s per question against 0.12 s); the 512-token cut was checked and does not explain it | Adopting it for its better hit@5 (not detectable); a longer token limit (not run, no pre-registration) |
| 83 | 15 Oct 2026 | A question-rewriting step is the working candidate: the question followed by a rewrite in the law's own vocabulary (R6.2), to be confirmed once on the test half with rewrites from the same prompt before it enters the final pipeline | On the development questions recall@5 rises from 0.53 to 0.70 (paired +0.169, interval +0.040 to +0.315); replace alone gives 0.68 (+0.148, +0.030 to +0.282) and the rule keeps the higher; rewrites were made by a separate agent that saw only the question texts and are stored in eval/rewrites | Rewrite alone (better MRR, not detectably different); no rewriting |
| 84 | 15 Oct 2026 | The in-pipeline rewrite step is not adopted yet: no Gemini Flash-Lite rewriter shows a detectable gain; the baseline retriever stays BGE-M3 alone (recall@5 0.53) and the agent's 0.70 is an upper bound, not the system's score | Four variants give +0.03 to +0.105 with every lower bound below 0 (the best, R6.6, -0.032 to +0.258); a stronger Flash model could not be tested on the free tier (20 requests a day) | Adopting the best point estimate; pooling non-significant results; more prompt tuning on the development half (ruled out in advance) |
| 85 | 15 Oct 2026 | Step 1 of the answer layer (language, jurisdictions, stated date) is plain rules in `answer/understand.py` | Language 40/40 and jurisdictions exactly right 35/40 on the development questions; free, instant, explainable; the rules were written knowing the development labels so the test half decides | A model call for something rules do well |
| 86 | 15 Oct 2026 | The pipeline routes with the model router; the rule router stays as a free baseline and a fallback | Model router 40/40 against 39/40 for the rules (one false table alarm); neither refused a question it should have answered; only 5 refusals and 4 table questions in the development half | Rules only; no router (everything retrieved) |
| 87 | 15 Oct 2026 | The model picks the table row, behind the router; the embedding lookup is kept out of the pipeline | The picker was right on 4 of 4 and the embedding lookup on 3 of 4; the picker's 3 false picks on non-figure questions broke my pre-registered limit of 1 but the router prevents them from reaching it (no retrieve question was answered from the table end to end) | Embedding lookup; the rule |
| 88 | 15 Oct 2026 | The answer layer's baseline configuration is five passages, the current text unless a date is stated, every quotation checked in code, an answer with no valid quotation turned into an abstention | Eight passages gave +0.016 in correctness (interval -0.065 to +0.113), so no change; the checking makes a fabricated quotation impossible to show | Eight passages; trusting the model's citations |
| 89 | 15 Oct 2026 | The project does not claim that retrieval makes answers more correct than the same model's memory: on the development questions judged correctness was 0.68 against 0.63 (+0.048, interval -0.097 to +0.177); its value is verifiable citations, refusal, version labels and texts newer than the model's training | The measured result; the judge was too generous on 2 of 12 answers a person read, so all correctness figures are probably a little high | Claiming an accuracy gain |
| 90 | 15 Oct 2026 | Version-aware search (text as first published for questions dated before 27 July 2026, every version for questions about the original wording) is built and tested but not adopted until it is measured | It fixes two diagnosed development failures (q044, q048) but is tuned on them; the measurement was blocked by the free-tier quota | Adopting it unmeasured |
| 91 | 15 Oct 2026 | Both Gemini clients stop at once when a quota resets in more than five minutes, and report it; experiments are scheduled around the free tier's 500 requests a day for gemini-3.1-flash-lite | A 9-hour retry delay made a run look frozen for 11 minutes; the earlier embedding stall may have been the same | Sleeping through the delay |
| 92 | 15 Oct 2026 | No jurisdiction or language filter is adopted; searching all texts stays | Even filtering by the gold jurisdictions (an upper bound) leaves recall@5 at 0.53; filtering by jurisdiction and language gives +0.032 with an interval starting at 0.000 | A jurisdiction filter; a language filter |
| 93 | 15 Oct 2026 | The demo is a standard-library web server around a service layer that limits (6 questions a minute per client, 300 a day overall, 1,000 characters), hides internal errors and writes a trace of every question without the client's address | Every question costs model calls; limits must come before the page; the trace is how failures are found after shipping; the standard library avoids a new dependency for a one-page demo | A web framework now; no limits; logging addresses |
| 94 | 15 Oct 2026 | The tested deployment path is BGE-M3 on the server's CPU (0.12 s per question, memory 4 GB or more); the Gemini embedding alternative waits for billing and a measurement | CPU speed was measured; the Gemini embeddings never finished on the free tier so their quality is unknown | Deciding on the unmeasured option |
